# 面试口述稿 · 本地知识库 RAG 问答

> 一条原则：别背功能，讲「三个决策 + 一组数字」。
> 面试官只关心：你为什么这么做、怎么验证、结果如何。

## 1. 一句话版（10 秒，自我介绍里带过）

> “我做过一个本地文档问答的小系统：把 PDF 切块，用字符级 BM25 检索，再把命中的段落连页码喂给本地 Qwen 生成答案。自己建了 15 道题的评测集，Hit@3 是 93%。”

## 2. 电梯版（40 秒，面试官问“讲一个你的项目”）

> “起因很简单：看论文和手册的时候想直接问，不想一页页翻。市面上的框架比较重，我就想自己把链路走通。
>
> 链路四步：PDF 解析、按句分块、字符级 BM25 检索、本地 Qwen 生成，回答带页码。
>
> 为了不靠感觉调参，我建了 15 道事实题的评测集，对比了三种检索方案，最后 Hit@1 87%、Hit@3 93%、Hit@5 100%。
>
> 比如问‘模拟退火设置了多少次搜索’，它能定位到第 23 页，答出 100 万次。”

## 3. 完整版（2 分钟，坐下聊）

**背景**
> “我想解决的是‘文档问答要能溯源’。答得快没用，得告诉我这句话在第几页。”

**约束**
> “三个限制：第一，不想上 LangChain 这种重框架，链路只有四步，我想控制每一步；第二，机器没有 GPU，只能跑 7B 的量化模型；第三，要能离线演示，不能没网就废。”

**决策一：分块**
> “360 字一块，块之间重叠一句。太小会把一个事实切成两半，太大检索就不精准；重叠是为了防止答案正好卡在边界上。每块都带页码，回答才能溯源。”

**决策二：检索（重点讲）**
> “中文没分词，我对比了三种：bigram BM25、unigram BM25、还有 RRF 融合。
>
> 结果是 unigram 最好，Hit@1 87%，bigram 只有 53%。原因很直接：中文短问句里 bigram 太稀疏，问句和原文差一个字就整段失配；unigram 召回高，靠 IDF 把‘的、是、年’这种高频字压下去。
>
> 融合反而没赢，73%。因为两路信号同质，都是字面统计，错误是高度相关的，融合只是把共同错误排到前面。要有语义 embedding 这种互补信号，融合才有意义。”

**决策三：数据清洗**
> “中间发现一个比调参更有用的事：论文附录是代码，中文占比很低，检索时全是噪音。我按中文占比低于 25% 直接过滤，块数从 91 降到 47，Hit@1 又从 80% 涨到 87%。这件事让我确认：脏数据比模型更影响效果。”

**决策四：生成与防幻觉**
> “生成用 Ollama 的 qwen2.5:7b，温度 0.2。提示词里写死三条：只依据资料回答、资料里没有就说没有、句末标页码。检索分数太低就直接回‘资料中没有提到’。另外没装模型时自动降级成抽取式回答，保证任何机器上都能演示。”

**结果**
> “15 道题，Hit@1 87%、Hit@3 93%、Hit@5 100%，MRR 0.913；检索本身是毫秒级。”

**反思**
> “两个不足：一是纯字面检索解决不了同义改写，比如问‘规划期’匹配不到‘2024—2030’，下一步接 embedding 做混合检索再加重排；二是评测集只有 15 题，只能用来排除明显更差的方案，不能代表线上效果，真要上线会扩到 100 题以上并分 dev/test。”

## 4. 追问速答

**Q：为什么不用 LangChain / 向量数据库？**
> “链路只有四步，数据量也不大，自己写四百多行能控制每一步、好调试。框架的价值在复杂编排，这个场景用不上；向量库要额外的 embedding 服务和索引，这一版先用字面检索打底，把评测跑通。”

**Q：为什么 unigram 比 bigram 好？**
> “中文短问句里 bigram 太稀疏，差一个字就匹配不上；unigram 召回高，靠 IDF 压高频字。代价是精度略低，但 Top-5 仍然是 100%。”

**Q：RRF 为什么没赢？**
> “两路都是字面统计，错误高度相关，融合只是放大共同错误。要互补信号才有意义。”

**Q：Hit@k 怎么算的？15 题会不会过拟合？**
> “每题标两个关键词，前 k 个块里只要有一个同时包含这两个词就算命中。15 题确实少，所以我只拿它排除明显更差的方案，没有据此精调超参；上线会扩到 100 题以上，分 dev 和 test。”

**Q：怎么防幻觉？**
> “三层：提示词限定只依据资料、强制标页码、低分直接拒答。更稳的是生成后再做一次答案和原文的蕴含校验，这块我还没做。”

**Q：文档到 10 万页怎么办？**
> “现在全量重建索引肯定不行。要换向量库 + 增量索引，检索分两段：先召回 50 条，再 rerank 取 5 条。”

**Q：这个项目最难的地方？**
> “不是写代码，是定评测标准。‘什么算答对’要先想清楚，否则调参没有方向——我一开始没定关键词，指标忽高忽低，后来把判定规则固定下来，对比才有意义。”

**Q：你一个人做的？**
> “是，从解析、分块、检索、评测到 Ollama 接入都是我一个人写的。”

**Q：为什么用字符级，不用 jieba 分词？**
> “不想引入词典依赖，而且领域词（比如‘重茬’‘羊肚菌’）分词器不一定认得；字符级更稳，代价是索引大一点，这个数据量完全无所谓。”

## 5. 必须记住的数字

| 数字 | 含义 |
| --- | --- |
| 47 | 清洗后的块数（原始 91） |
| 15 | 评测题数 |
| 87% / 93% / 100% | Hit@1 / Hit@3 / Hit@5 |
| 0.913 | MRR |
| 53% | bigram 的 Hit@1（对照） |
| 73% | RRF 融合的 Hit@1（对照） |
| 360 / 1 句 | 分块大小 / 重叠 |

## 6. 不要说的话

- ❌ “上线了 / 服务了多少用户”——没有，别编。
- ❌ “用了 LangChain / 向量数据库 / FAISS”——没有，被追问会穿帮。
- ❌ “准确率 93%”——是**检索命中率 Hit@3**，不是回答准确率，两回事。
- ❌ 没跑过 Ollama 之前，别说“本地大模型生成效果很好”；跑过再讲效果。
- ❌ 别把它吹成工业级系统；说清楚“个人项目、单文档、评测集小”，反而可信。

## 7. 现场演示动线（如果让你演示）

```bash
python app.py eval
python app.py ask "普通大棚和智慧大棚分别有多少个？" --show-context
python app.py ask "模拟退火设置了多少次搜索？" --backend ollama --stream
```

先跑 eval 给数字，再问一个能命中原文的，最后展示带页码的回答。
`--show-context` 用一次就够，让面试官看到“检索到了什么”，别刷屏。
